# `ascent-path-export.json` — what this is and how to use it

This is a **test fixture** for splashcast to develop/test its "add your rocket"
ascent-side integration against, before the real `rocketry` library bundle
exists. It's the exact JSON shape `rocketry`'s `buildAscentPath()` produces
today, generated by `scripts/export-ascent-path.ts` in the `rocketry` repo.

Regenerate it any time with:
```
cd rocketry && npx tsx scripts/export-ascent-path.ts
```

## Why this data, specifically

- **Rocket geometry** is real: LOC Precision "PK-48 LOC-IV" (4" airframe),
  transcribed from an actual RockSim `.rkt` file and cross-checked against
  RockSim's own stored CP value.
- **Motor** is real: AeroTech K400C, fetched live from ThrustCurve.org (not
  synthetic/made up).
- **Wind** is real: the actual captured file
  `sim-files/wind/hutto_splash_zones_captured_2026-08-10.json`, hour 9,
  GFS model — the same file/format splashcast itself produces from
  Open-Meteo.
- **`dryMass`/`dryCg` are estimated placeholders**, not from a real spec
  sheet — this tool's design has mass/CG entered manually rather than
  computed from materials, and no published dry-weight figure for this kit
  was available. They're picked to land at a normal ~1.5-caliber stability
  margin so the fixture exercises the ordinary case, not an edge case. See
  `_meta.caveats` in the file itself.
- The resulting apogee (~7986 ft / 2434 m AGL) lands inside the altitude
  bands your own `altitudes` field already expects (`[2000, 4000, 6000,
  8000, 10000]` ft), and is high enough to actually cross into this wind
  profile's real directional shear layer (~190° near the ground, rotating to
  ~134° by ~8300 ft) — so `windShear` in this file is a genuine, non-trivial
  -54°, not noise. A low-altitude rocket on a weaker motor would correctly
  show ~0° shear here; that's real physics (verified in
  `src/physics/sim/ascent-path.test.ts`), not a bug to work around.

## What problem this solves

Today splashcast approximates the boost phase with a fixed `boost_angle_deg`
(10°) and a flat `max_pad_move_ft` (2000 ft) — no real physics. `rocketry`
replaces that with an actual RK4 3D flight simulation (nose cone → fins →
motor → wind, integrated to apogee) and packages the result as **named
waypoints and a path**, mirroring the shape your descent side already uses
(`simulate()`'s altitude-stepped drift path with named deploy points), so the
two halves of the flight — boost/coast up, drogue/main down — can be plotted
as one continuous 3D trajectory instead of a straight line up and a separate
simulation down.

## Field-by-field

### `_meta`
Provenance/caveats only — not simulation output, don't plot it.

### `rocket`
The inputs used: dry mass/CG (kg / m from nose tip), motor summary, launch
site altitude (m ASL), launch rod length (m).

### `stability`
- `marginCalibers` — CP−CG distance in body diameters. `flyable: false` means
  CG was behind CP (would not fly straight) — check this before trusting the
  rest of the file for any *other* generated fixture; this one is flyable.
- `warnings` — human-readable strings (low margin / overstable / not
  flyable), already the same warnings shown in `rocketry`'s own UI.

### `summary`
The single-number handoff values — closest to what your current
`boost_angle_deg`/`max_pad_move_ft` placeholders are meant to be replaced by:
- `apogeeAltitudeFt` / `apogeeAltitudeM` — feed this as your descent side's
  starting altitude instead of guessing.
- `apogeeTimeS` — seconds from liftoff to apogee.
- `burnoutAltitudeFt` / `burnoutAltitudeM` — motor burnout altitude (may be
  `null` if the motor never burned out, e.g. didn't ignite).
- `tiltAtBurnoutDeg` — the real weathercocking-severity number (NOT
  flight-wide max tilt — tilt legitimately approaches ~90° near apogee for
  *any* stable rocket as vertical velocity vanishes near the top of the
  arc; that's expected, not an instability signal).
- `maxVelocityMs`, `maxMach` — for context/sanity-checking.
- `warnings` — flight-level warnings from the simulation engine itself
  (separate from the `stability.warnings` above).

### `windShear`
Ground wind vs. wind at apogee altitude, plus the deltas. This is what makes
"weathercocks into ground wind near the pad, turns into a different wind
aloft near apogee" a claim backed by the actual wind profile rather than
narration:
```json
{
  "ground": { "vx", "vy", "speed", "directionFromDeg" },
  "aloft":  { "vx", "vy", "speed", "directionFromDeg" },
  "speedDeltaMs": "aloft.speed - ground.speed",
  "directionDeltaDeg": "shortest signed angular diff, aloft - ground, in [-180, 180]"
}
```
`vx`/`vy` are East/North m/s components (not speed+direction) specifically to
avoid compass-wraparound bugs if you do vector math directly instead of using
`speed`/`directionFromDeg`.

### `waypoints` (array, chronological: LIFTOFF → LAUNCHROD → BURNOUT → APOGEE)
Each waypoint is a labeled, physically real moment in the flight:
```json
{
  "type": "BURNOUT",
  "label": "Motor burnout",
  "time": 3.14,                 // s since liftoff
  "position": { "x", "y", "z" },// m, world frame: x=East, y=North, z=up AGL
  "altitude": 727.6,            // m AGL, = position.z
  "tiltFromVerticalDeg": 8.8,   // weathercock angle at this instant
  "aoaDeg": 3.2,                // angle of attack
  "speed": 145.0,               // m/s, ground-relative
  "wind": { "vx", "vy", "speed", "directionFromDeg" } // wind AT THIS ALTITUDE
}
```
These are the four marker points you'd drop pins/labels on in a 3D view —
directly analogous to your descent side's named deploy points (drogue/main).

### `segments` (array, 2 entries: LAUNCHROD→BURNOUT, BURNOUT→APOGEE)
Pre-written labels + auto-generated description strings for the two "acts" of
the ascent, with real numbers already substituted in (wind speed/direction,
tilt angles) — usable directly as UI copy/tooltips, or as a template if you
want your own wording:
```json
{ "from": "LAUNCHROD", "to": "BURNOUT", "label": "Weathercocking into ground wind", "description": "..." }
```

### `path` (array, 80 points, evenly spaced in TIME from liftoff to apogee)
The actual curve to draw. Each point:
```json
{ "time", "position": { "x", "y", "z" }, "altitude", "tiltFromVerticalDeg" }
```
Resampled in **time**, not altitude — altitude isn't monotonic if the rocket
noses over hard before apogee, so a fixed time step is the robust choice.
Point count is fixed at 80 regardless of flight duration, so short and long
flights both render at a consistent resolution. `position` is in the same
world frame as waypoints (x=East, y=North, z=up AGL, meters) — if your
descent-side path uses a different local coordinate convention (e.g.
lat/lon-derived equirectangular meters), you'll need to align origins/axes
before splicing the two paths together; check `simulateDrift()`'s coordinate
setup on your side for the exact convention it expects.

## Known limitation / what's still coming

This file is hand-generated from a placeholder rocket (real geometry + real
motor, but estimated mass/CG). The actual handoff API — something like
`Rocketry.simulateFromOrk(orkBytes, motorSelection, windProfile) →
AscentResult` — that takes a real uploaded `.ork`/`.rkt` file plus a
ThrustCurve.org motor selection and produces this exact JSON shape live in
the browser, is not built yet. Once you've validated your rendering against
this fixture, that's the next piece — no schema changes expected on your end
when it lands, just a live call instead of a static file.
